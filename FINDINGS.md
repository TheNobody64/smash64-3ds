# Old 3DS CPU-bound optimization pass: findings

Builder 1.2.4 · static analysis of the compiler/build pipeline and the game, port, and renderer code, plus x86 equivalence tests for the code I changed.

> **Nothing here has been compiled for ARM or run on a 3DS or in Azahar. No gain below is measured.** Gains marked [E] are my estimates from instruction counting and call-frequency reasoning. Your own `docs/OLD-3DS.md` already says the 1.2.3 and 1.2.4 changes have never been compiled for ARM, so everything in this bundle sits on top of that same untested baseline.

## 0. How to read this

**Evidence tags**

| Tag | Meaning |
|---|---|
| **[V]** | Verified by a test in `verify/` (run `run_tests.sh`). |
| **[S]** | Static evidence in source, cited as `file:line`. |
| **[E]** | Estimate. Needs a measurement before you trust the size of it. |

**Scope.** "Compiler" means the clang flags, the build driver (`tools/build*.py`), and the generators (`prepare_*.py`). "Game code" means the decomp (`vendor/BattleShip/decomp`), the port layer (`vendor/BattleShip/port`), and the 3DS platform and renderer (`3ds/src`, `3ds/renderer`).

**Generated code.** `renderer/gfx_pc.c` is produced by `prepare_render.py` and is not in the zip. Line numbers below refer to the file I regenerated by running the generator. Apply any renderer change in the generator, not in the output.

**"Exact"** means bit-identical output to the current code. Anything not exact is labelled.

## 1. Where the time probably goes

On Old 3DS the profile in `hardware.c` runs game logic, scheduler, audio synthesis, display-list translation and GPU submission serially on one 268 MHz core with no L2. So the useful question is which per-frame work scales with something large:

| Work | Scales with | Why it matters here |
|---|---|---|
| Fast3D translation (`gfx_pc.c`) | triangles, vertices, texture loads | Fighters are a likely large source of both. Your observed drop from ~30 to ~20 FPS when fighters appear points here, though it also includes fighter logic. |
| Texture load path | texture loads per frame | Every load copies up to 4 KB, refills a 512-entry origin table, and hashes the bytes (see R2, R3). |
| Draw submission | number of flushes | Each flush builds a `NativeDraw` and later replays through citro3d, all on the same core (R6). |
| Audio synth | active voices × 32 kHz | 16 physical voices, ~533 output samples per frame each, portable C with no SIMD (A1). |
| Reloc token resolution | resolves per frame | 335 `PORT_RESOLVE*` call sites, each an out-of-line call into a C++ TU (G1). |
| Fighter AI | CPU fighters | `syUtilsArcTan` has 5 chained divides and ~100 call sites (G3). |

I could not rank these with real numbers. Section 9 shows how to get them with instrumentation you already have.

## 3. Compiler and build pipeline

| ID | Finding | Evidence | Fix | Gain / risk |
|---|---|---|---|---|
| **C1** | **Unaligned access is probably off.** For non-Linux ARMv6 bare-metal, clang's driver defaults to strict alignment (from my recollection of the clang driver source, so verify it). devkitARM's GCC defaults the other way, and homebrew built with it relies on the CPU's unaligned `ldr`/`str`. | Your `native_texture_hash.h` comment says unknown-alignment `memcpy` "becomes four byte loads and shifts for every word on ARM11". That is the symptom. Flags: `build.py:31-32` (`ARCH`) has no `-munaligned-access`. | First confirm: compile `memcpy(&w,p,4)` with the pinned clang and look for `ldrb` vs `ldr`. Then A/B `SSB_GAME_CFLAGS=-munaligned-access` and `SSB_EXTRA_CFLAGS=-munaligned-access`. | [E] medium: affects struct copies, packed reads, byte-swap loops. **Risk:** unaligned `LDM`/`LDRD`/`VLDR` still fault. LLVM shouldn't emit those for unaligned-typed accesses, but test on hardware (Azahar will not fault). |
| **C2** | **The Fast3D interpreter is built with the decomp's conservative flags.** `gfx_pc.c` goes through `game_flags()` (`build_runtime.py:46`) and so gets `-fno-strict-aliasing -fwrapv`, while its sibling `gfx_citro3d.c` does not. In the per-triangle loop every `buf_vbo[..] = x` float store may alias `rdp.*`, `rsp.*`, `comb->*`, `used_textures[]`, forcing reloads. | `build_runtime.py:46-47`, `gfx_pc.c:1103-1170` | `SSB_RENDER_CFLAGS=-fstrict-aliasing` (later flag wins). **Prerequisite:** remove the float→`int32_t*` punning at `gfx_pc.c:899-902`, which is undefined behaviour under strict aliasing. R8 replaces it. | [E] medium for the renderer. Risk: other punning in the SM64-derived code. Check with the stage profile. |
| **C3** | **No LTO, and many tiny cross-TU calls on hot paths:** `PORT_RESOLVE`→C++ TU, `native_dl_check`, `nativeTextureAlive/Touch`, `nativeFixVertices`, `nativeUvConstants`, `nativeCombineTrace`, `ssb_osGetTime`. | Each is out-of-line because the callee is in another TU. | Preferred: manual inlining (R5, R12, G1), which gets most of the benefit without growing code. ThinLTO (`-flto=thin` through the hook) is possible but needs link-step changes I did not make. | Your doc's concern (small cache, no L2) is valid. Treat LTO as A/B only. |
| **C4** | **One optimization level for everything.** Menus (`mn`, ~44 k lines), movies, credits and debug code get the same `-O2` as collision and animation. No per-file mechanism exists. | `compile_game` uses a single `game_flags()` list. | Add a small per-directory table: `-O3` candidates for `gfx_pc.c`, mixer, `sys/matrix.c`, `sys/objanim.c`, `lb/lbcommon.c`, `mp/mpcollision.c`; `-Os` for cold directories to protect the I-cache. | [E] low-medium, uncertain sign. A/B only, which your doc already argues. |
| **C5** | **Any header edit rebuilds all ~600 objects.** The comment says "compiler dependency files handle headers", but the up-to-date test only compares each object's mtime with its *source* mtime. The `.d` files that `-MMD` writes are never read; headers are instead hashed into the flags stamp, so touching one `.h` invalidates everything. The support library (`build_support.py`) has no cache at all and recompiles every run. | `build.py:78-100` | Read the `.d` files for per-object invalidation; give `build_support.py` the same mtime check. | Dev-loop speed only, but it makes the A/B experiments above much cheaper. |

## 4. Renderer (generated `gfx_pc.c`, `gfx_citro3d.c`, `native_render_queue.h`)

| ID | Finding | Evidence | Fix | Gain / risk |
|---|---|---|---|---|
| **R1** | **The whole draw state is re-validated on every triangle.** Per triangle: build `cc_id` (~25 branchy statements), a function-pointer `shader_get_info`, a `NativeTile` struct copy per used unit, per-axis clamp/mask math, `nativeTextureAlive` + `nativeTextureTouch` (cross-TU), sampler compare, `nativeUvConstants` ×2, `nativeCombineTrace`, `nativeDiagActive`, then a `switch` per colour input inside the vertex loop. | `gfx_pc.c:863-1190` | Add a `state_epoch` counter bumped by `SETCOMBINE`, `SETOTHERMODE_L/H`, `G_TEXTURE`, `SETTILE`, `SETTILESIZE`, `LOAD*`, geometry-mode and fog commands. In `gfx_sp_tri1`, redo the validation only when `epoch != validated_epoch`, caching `prg`, `num_inputs`, `used_textures`, UV constants and flags in a small struct. Keep the masked-clamp UV scan dynamic. Keep aliveness checks at flush/upload boundaries. | [E] **high.** Several hundred cycles/triangle × ~2 000 triangles is ~2-4 ms. Likely the largest single renderer item. Needs the stage profile to confirm. |
| **R2** | **Redundant texture state forces a flush, a re-import and a re-hash.** `textures_changed` is set unconditionally in `nativeTmemWrite` (every load), `G_TEXTURE`, `G_SETTILE`, `G_SETTILESIZE` and `G_LOADTLUT`, even when the new values equal the old. `G_LOADTLUT` also re-hashes the 512-byte palette each time. The next triangle then runs `gfx_flush()` + `import_texture()`, which hashes up to 4 KB. | Set at `gfx_pc.c:380, 1304, 1337, 1345, 1356`; consumed at `:1035-1038`; `nativeTextureAlive` re-checked per triangle at `:1028` | Compare incoming values to current state and set the flag only on change. Memoize the content hash per `(src ptr, size)` for the current frame (invalidate through the existing capture/free hooks). Hash values are purely internal; I grepped, and nothing persists or compares them outside the cache lookup. | [E] **high when it triggers.** Unknown frequency. Add counters first: `import_texture` calls vs. distinct textures. |
| **R3** | **TMEM emulation costs a copy, a table fill and a serial hash for every load.** `nativeTmemWrite` `memcpy`s up to 4 KB and writes up to 512 `tmem_origin` entries; the hash is FNV-1a, a dependent multiply chain, over up to 1 024 words. | `gfx_pc.c:376`, `native_texture_hash.h` | Use 4 independent hash lanes (hash value is internal), fill `tmem_origin` lazily, or skip the copy when the same source/size/offset was just loaded. | [E] ~10-15 k cycles per full-size texture. Medium, scales with R2. |
| **R4** | **The texture cache pool is only 512 entries and wipes everything when full.** | `gfx_pc.c:344-350` (`pool_pos = 0`), `:95`. You already log hits/misses every 180 frames (`:2008`). | Check `misses` in that log first. If high, grow the pool and use clock/LRU replacement instead of flush-all. Add a wrap counter. | [E] unknown. Potentially large stutter after each wrap (everything re-decodes and re-uploads). |
| **R5** | **Eviction is an O(4096) scan per evicted texture**, and the loop condition calls `linearSpaceFree()` every iteration. | `gfx_citro3d.c:83-103` | Evict in one pass from an age histogram until the target is met. Check what `linearSpaceFree()` costs in libctru; if it walks heap metadata, it is expensive in a loop. | [E] only under memory pressure, but that is exactly your Old 3DS case. |
| **R6** | **Redundant flushes.** `G_SETCOMBINE` and `G_SETBLENDCOLOR` flush unconditionally, even when the value is unchanged. Each flush costs a `NativeDraw` build (six TexEnv copies, two `C3D_Tex` copies, a `memcmp` chain), even though the queue later merges identical neighbours. | `gfx_pc.c:1787, 1804`; `native_render_queue.h` (`nativeQueueDraw`) | Skip when all inputs to the combine/second-cycle derivation are identical to the last call (`w0`, `w1`, `other_mode_h`, env, prim). Check no other path writes `rdp.combine_mode`. | [E] medium. Draw count is a CPU driver on this device. |
| **R7** | **Each vertex is copied twice.** `gfx_sp_tri1` writes 12+ floats/vertex into `buf_vbo` (256×78 floats ≈ 78 KB, more than a small L1), then `draw_triangles` copies them again into the VBO just to apply UV scale. Texture scale is known at triangle time, because a texture change flushes first. | `gfx_pc.c:192`; `gfx_citro3d.c:705-750` | Apply UV scale in `gfx_sp_tri1` and write straight into the final VBO. | [E] medium: ~100-150 cycles/triangle plus cache traffic. |
| **R8** | **Culling uses 3 `vdiv` per triangle** (non-pipelined on VFP11) plus float→int pointer puns. | `gfx_pc.c:884-902` | `oops = ~signbit(det) ^ cull_front<<22`, where `det` is the 3×3 determinant of `(x,y,w)`. The `w` signs cancel algebraically, so no divide and no pun (use `memcpy` for the bit cast). | [V] disagrees with the current test in 0.117 % of 40 M synthetic triangles, **all** with \|NDC cross\| < 1.1e-6 (sub-pixel slivers). Against double-precision truth the *current* code is itself wrong on those. **Not bit-exact** but visually equivalent. Saves ~40 cycles/triangle [E]. Also unblocks C2. |
| **R9** | **Int→float colour conversion per vertex.** `color->r * (1.0f/255.0f)` is a `vmov` + `vcvt` + `vmul` on VFP11, repeated for every triangle that touches a vertex (each vertex is used by 3-6 triangles). | `gfx_pc.c:1162-1170` | 256-entry `float` LUT (1 KB). Better still: convert once at `G_VTX` time. | [V] LUT is bit-identical for all 256 values. [E] low-medium. |
| **R10** | **Debug checks run in release.** A `volatile` `ssb_frame_count==850 && ssb_test_logging` test per triangle and per vertex-unit (volatile loads cannot be hoisted), `nativeCombineTrace(...)` per triangle, `nativeDiagActive()` per triangle, and 23 `SUPPORT_CHECK` asserts. | `gfx_pc.c:873, 963, 1052`; `:38` | Compile out under `#ifndef SSB_BENCH`; keep the asserts only in bench/debug builds. | [E] low-medium. Bounds-check asserts are a trade-off against crash detection, so your call. |
| **R11** | **The MP matrix is rebuilt after every matrix op, including pops.** | `gfx_sp_matrix_impl` (`:698-735`) and `gfx_sp_pop_matrix` (`:738`) each end with a 4×4 multiply (~64 MACs). A pop is almost always followed by another push or mul. | Mark `MP` dirty on mtx/pop and recompute at the next `G_VTX`. | [E] saves roughly a third of matrix multiplies. Exact. Low-medium. |
| **R12** | **Per-command overhead.** `native_dl_check(cmd)` is an out-of-line call per DL command, and `nativeResolveGfxAddress` → `portRelocTryResolvePointer` runs for every pointer-carrying command. | `render_bridge.c:147-148`, `gfx_pc.c:1657` | Check the DL bound inline against a cached `[start,end)`; apply the 500 000-command guard per DL, not per command. See G1 for the resolver. | [E] roughly 10-15 cycles saved per DL command, so it scales with command count (unmeasured). Exact. |
| **R13** | **Lighting accumulates in `int` with a float→int convert per light.** | `gfx_pc.c:806+` | Accumulate in float and convert once. | [E] low. **Not exact** (≤1 LSB of colour per light). |
| **R14** | **Unmeasured:** `nativeQueueDraw` copies a few hundred bytes per flush. | `native_render_queue.h` | Track dirty bits instead of copying and comparing all state. | [E] depends on flush count; do R6 first. |

## 7. Structural options (large, unverified)

1. **Move the vertex stage to the PICA200.** The renderer still translates every vertex on the CPU, which your own doc notes. From the DObj/matrix structure in `objdisplay.c`, fighters appear to be drawn as rigid joints with one matrix each, so each joint's `Vtx` block would be static model-space data plus a matrix, which is a good fit for a GPU vertex shader (I have not verified this against every model). A sketch: cache the vertex block per `Vtx*` range (reusing the existing fixup/eviction invalidation), upload it once, and have each `G_TRI` push only indices. That removes the per-vertex transform and the 12-float-per-vertex expansion. This is the only item here I think could plausibly change the renderer's cost by a large factor, and it is also the biggest and riskiest. Lighting, fog and combiner inputs must move to uniforms.
2. **Decouple render rate from logic rate** (render every other frame), but only if `game+scheduler+audio` in your THREADS line is comfortably under 16.7 ms.
3. **Use the second core** (`render_core=1`). Your doc says the share APT grants is unknown. Texture import (decode + swizzle) is a more separable candidate than the whole renderer.

## 9. Measurement plan (uses instrumentation you already have)

1. Run one baseline per scene on hardware, saving `THREADS`, `STAGES` (build with `SSB_STAGE_PROFILE` via `SSB_EXTRA_CFLAGS`), `TEXTURE_CACHE hits/misses`, `Texture reclaim` and `DEGRADED` lines, plus the bench CSV `render_ms`. Keep emulator and hardware results in separate tables, as you do now.
2. Apply the decision rule from your own doc: if `game+scheduler+audio` alone is near 16.7 ms, renderer work cannot reach 60 FPS, and the game side is the lever. If `render_ms` dominates, work through R1 → R2 → R6 → R7.
3. Add four counters before changing R1-R6, so each fix is justified by data:
   - `import_texture` calls and bytes hashed per frame
   - tile updates whose values didn't change
   - flushes (and draws) per frame
   - texture-cache pool wraps
4. Change one thing at a time. Both `SSB_GAME_CFLAGS` and `SSB_RENDER_CFLAGS` trigger a clean rebuild automatically through the flags stamp.

## 10. Honest ceiling

Your reported numbers are ~30 FPS (≈33 ms) on an empty stage and ~20 FPS (≈50 ms) with fighters. Sixty FPS needs ≤16.7 ms, a ~3× reduction. The exact changes in this bundle, even combined with every [E] item in sections 3-5, are in my estimate more likely to move that by a modest fraction than by 3×. I can't prove that without measurements. If the profile shows fighters' translation and texture handling dominate, the PICA vertex path in §7 is the one that could close the gap. Everything else buys headroom.
